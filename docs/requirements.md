# Telegram 消息采集与 AI 总结系统需求文档

- 文档状态：需求草案，关键业务口径已确认
- 当前阶段：本机开发与测试
- 后续阶段：本机验收通过后，部署至无图形界面的 Ubuntu 服务器
- 更新日期：2026-08-29

## 1. 项目背景

用户需要收集其 Telegram 账号有权访问的群组和频道消息，按照消息来源分类保存，并调用 AI 分别总结各群组或频道的内容。

项目必须先在本机完成开发、测试和验收；本机验收通过前，不执行服务器上传、部署或长期运行配置。

## 2. 项目目标

1. 通过 Telegram 用户账号采集指定群组和频道中的可见消息。
2. 按稳定的群组或频道标识分类存储消息，避免名称变化造成数据混淆。
3. 持续采集新增消息，并正确处理重复消息和消息编辑。
4. 按群组或频道分别调用 AI 生成内容总结。
5. 原始消息与对应总结仅保留有限时间，到期后同步删除。
6. 本机测试通过后，可迁移到无图形界面的 Ubuntu 系统运行。

## 3. 当前业务口径

### 3.1 消息规模

- 日常消息量：预计每天 1 万至 2 万条。
- 基准估算：每天 1.5 万条。
- 消息类型：当前版本只处理纯文本内容。
- 不下载图片、视频、语音、压缩包及其他媒体文件。
- 媒体消息如包含文字说明，可将说明文字作为文本消息处理；媒体本体不下载、不解析。

### 3.2 数据保留范围

- 逻辑保留范围：当天及过去 5 天，共 6 个自然日。
- 计划每周执行一次物理清理。
- 由于清理周期为 7 天，数据库在清理前最多可能临时保存约 13 个自然日的数据。
- 按每天 2 万条估算，清理前峰值约为 26 万条消息。
- “到期”定义为每周清理任务运行时，数据早于当次业务日期计算出的保留截止点。
- 到期原始消息无论是否总结成功都必须删除，不得因 AI 失败延长保留时间。
- 与到期原始消息对应的总结结果和 Markdown 文件同时删除。

### 3.3 “所有消息”的定义

本项目中的“所有消息”是指：

- 指定来源中，Telegram 账号当前有权限读取的消息；
- 位于配置的保留时间范围内；
- 包含可处理文本内容；
- Telegram 仍然提供且尚未删除的消息。

以下内容不属于可保证采集范围：

- 当前账号无权访问的私密来源；
- Telegram 已删除且采集器从未见过的消息；
- 账号加入前不可见的历史消息；
- 媒体文件中的图像、音频或视频内容。

## 4. 实施阶段与上线门禁

### 4.1 第一阶段：本机开发与测试

第一阶段只在本机执行，目标包括：

1. 完成 Telegram 登录和会话保存。
2. 使用人工白名单配置真实频道，并以只读方式完成测试；如白名单包含群组，则同时测试真实群组。
3. 完成最近 6 个自然日的首次同步。
4. 完成实时增量采集。
5. 完成消息分类、去重和编辑更新。
6. 完成按来源的 AI 总结。
7. 完成过期消息清理验证。
8. 完成异常恢复和中断续传验证。

### 4.2 第二阶段：Ubuntu 部署

仅当第一阶段验收项全部通过，且用户明确批准后，才允许：

- 将项目上传至 Ubuntu 服务器；
- 安装服务器依赖；
- 传输或重新创建 Telegram 会话；
- 创建 `systemd` 服务和定时任务；
- 配置长期运行、备份和日志轮转。

本阶段需求文档只规定服务器兼容性，不执行实际服务器操作。

## 5. 用户角色

当前版本只有一个系统使用者：

- 系统管理员：配置 Telegram 账号、目标来源、AI 接口、运行计划和保留策略，并查看总结结果与运行状态。

当前版本不提供多用户权限系统和 Web 管理后台。

## 6. 功能需求

### FR-01 Telegram 应用配置

系统应支持配置：

- Telegram `api_id`；
- Telegram `api_hash`；
- 登录手机号；
- Telegram 会话文件位置；
- 两步验证登录流程。

敏感配置不得写入源码、提交到版本控制或打印到日志。

### FR-02 Telegram 登录

系统应提供一次性的交互登录命令。

登录成功后：

- 将会话持久化到本地受限文件；
- 后续运行无需重复输入验证码；
- 会话失效时给出明确错误，不自动反复请求验证码。

### FR-03 来源配置

系统应只采集人工白名单中明确启用的群组和频道，不得默认采集账号加入的全部来源。白名单通过配置文件维护。

每个来源至少保存：

- 稳定的 `chat_id`；
- 当前标题；
- 用户名（如有）；
- 类型：群组或频道；
- 是否启用采集；
- 最近同步状态。

系统不得仅使用群组或频道标题作为唯一标识。

### FR-04 首次同步

首次同步默认只获取当天及过去 5 天内的可见文本消息，不回填全部历史数据。

首次同步必须：

- 按来源独立执行；
- 支持中断后继续；
- 分批写入数据库；
- 成功写入后再推进同步游标；
- 重复执行时不得产生重复记录。

如果后续需要对完整历史进行一次性总结，应作为独立需求另行确认，不纳入当前版本。

### FR-05 增量采集

系统应持续监听并保存：

- 新文本消息；
- 含文字说明的媒体消息；
- 消息编辑事件。

消息编辑后，`messages` 保存最新版本，同时将每个不同内容版本追加到编辑历史，不覆盖已有版本记录。

系统应在断线重连后主动补拉缺失区间，不能只依赖实时事件。

消息删除事件只能尽力同步；系统不承诺发现采集器离线期间发生且 Telegram 不再返回的删除。

### FR-06 消息去重

每条消息使用以下组合唯一标识：

```text
(chat_id, message_id)
```

重复采集同一条消息时：

- 不插入重复记录；
- 如果编辑时间或内容更新，则更新当前记录并追加编辑历史；
- 相同内容版本重复到达时，不得重复追加编辑历史；
- 同步游标不得因为重复数据而倒退。

### FR-07 消息分类

所有消息必须通过 `chat_id` 关联到唯一来源。

系统查询、总结和导出时，应能按照以下维度筛选：

- 群组或频道；
- 消息发送时间；
- 消息 ID 范围；
- 是否已被总结覆盖。

当前版本以数据库分类为准，不要求实时维护重复的 JSONL 文件副本。

### FR-08 数据存储

本机阶段使用 SQLite，要求：

- 开启 WAL 模式；
- 设置合理的锁等待时间；
- 使用批量事务写入；
- 数据库文件位于本地磁盘；
- 同一会话只允许一个采集主进程写入；
- AI 总结写回使用短事务。

至少需要以下数据对象：

1. `chats`：来源信息；
2. `messages`：当前保留窗口内的消息；
3. `message_versions`：消息初始内容及每次编辑历史；
4. `sync_state`：每个来源的同步游标和状态；
5. `summary_jobs`：AI 总结任务；
6. `summaries`：总结结果；
7. `cleanup_runs`：清理记录。

### FR-09 AI 接口配置

系统应接入 OpenAI 兼容接口，并允许用户自定义服务地址。至少支持配置：

- `base_url`；
- API 密钥；
- 模型名称；
- 请求超时时间；
- 最大重试次数；
- 单次输入上限；
- 总结提示词版本。

API 密钥不得存入数据库消息正文、源码或日志。

当前版本只实现 OpenAI 兼容协议，不要求为不同供应商分别实现专用适配器。

### FR-10 分块总结

由于单个来源每天可能包含大量消息，系统不得将任意规模的全部消息直接放入一次 AI 请求。

系统应：

1. 按来源隔离消息；
2. 按时间和输入长度拆分消息块；
3. 对每个消息块生成中间总结；
4. 将中间总结合并为来源级总结；
5. 保留输入时间范围、消息范围和输入哈希；
6. 相同输入、模型和提示词版本不得重复计费调用。

每天固定生成三个互不重叠且连续的总结窗口，业务时区为 `Asia/Shanghai`：

| 执行时间 | 总结窗口 | 区间定义 |
|---|---|---|
| 08:00 | 前一日 22:00 至当日 08:00 | `[前一日 22:00, 当日 08:00)` |
| 12:00 | 当日 08:00 至当日 12:00 | `[当日 08:00, 当日 12:00)` |
| 22:00 | 当日 12:00 至当日 22:00 | `[当日 12:00, 当日 22:00)` |

- 所有窗口使用左闭右开区间，边界消息只属于后一个窗口。
- 三个执行时间必须允许通过配置调整；调整后仍以“上一次计划执行时间至本次计划执行时间”生成连续窗口，不得重复或遗漏。
- 总结任务必须以来源、窗口开始时间和窗口结束时间唯一标识，所有边界转换为 UTC 后持久化。

### FR-11 总结内容

每份来源级总结至少包含：

- 来源名称；
- 总结覆盖时间；
- 主题；
- 重要信息；
- 主要观点；
- 消息来源，至少列出代表性消息的时间和消息 ID；
- 无法确认或存在冲突的信息说明。

总结使用中文固定结构，栏目名称统一为“主题”“重要信息”“主要观点”“消息来源”。

不得在没有消息依据时补充事实。

### FR-12 总结输出

总结结果应：

- 保存到 `summaries` 数据对象；
- 按来源输出 Markdown 文件；
- 文件名包含来源稳定标识、窗口开始时间和窗口结束时间；
- 重复执行同一总结任务时保持幂等；
- 支持按来源查看最近一次成功总结。

总结结果不长期保留。某个总结窗口对应的原始消息到期时，数据库总结记录及对应 Markdown 文件必须同步删除。

### FR-13 总结失败处理

AI 接口超时、限流或返回错误时：

- 不得阻塞 Telegram 消息采集；
- 记录失败原因和重试次数；
- 按策略自动重试；
- 超过最大重试次数后标记失败；
- 到达保留截止点后，即使总结仍失败，也必须停止重试并删除对应原始消息；
- 状态命令应能显示失败任务。

### FR-14 数据清理

系统应提供可手动执行和可定时执行的清理命令。

定时清理默认在 `Asia/Shanghai` 每周日 03:00 执行。

原始消息清理条件：

```text
消息早于业务日期的保留截止点
```

清理必须：

- 使用配置的业务时区计算自然日；
- 记录清理开始时间、结束时间和删除数量；
- 支持预览模式，只显示预计删除范围；
- 支持重复执行；
- 不以总结任务是否成功作为原始消息删除条件；
- 删除总结窗口结束时间不晚于保留截止点的总结记录和 Markdown 文件；
- 不删除来源信息、同步游标和清理记录。

### FR-15 时间处理

- 数据库存储时间统一使用 UTC；
- 业务自然日和总结调度统一使用 `Asia/Shanghai`；
- 每日总结执行时间默认配置为 08:00、12:00、22:00，并允许用户修改；
- 总结文件中应显示业务时区；
- 总结窗口边界必须由 `Asia/Shanghai` 换算为 UTC 后持久化和查询；
- 清理截止点必须由业务时区换算为 UTC 后执行。

### FR-16 状态查询

系统应提供状态查询命令，至少显示：

- Telegram 登录状态；
- 已配置来源数量；
- 每个来源最后同步时间；
- 每个来源最新消息 ID；
- 当前保留消息数量；
- 待处理、失败和完成的总结任务数量；
- 下一次总结执行时间及对应窗口；
- 最近一次清理结果；
- 数据库文件大小。

### FR-17 日志

系统日志至少包括：

- 启动和停止；
- 登录和连接状态；
- 各来源同步结果；
- Telegram 限流等待；
- AI 请求成功或失败；
- 清理结果；
- 未处理异常。

日志不得包含：

- Telegram 验证码；
- 两步验证密码；
- `api_hash`；
- AI API 密钥；
- Telegram session 内容；
- 完整私密消息正文。

### FR-18 备份与恢复

本机测试阶段至少支持：

- 在服务停止或数据库一致性可保证时备份 SQLite；
- 备份总结文件；
- 从备份恢复数据库后继续同步；
- 会话文件与消息数据库分开处理。

会话文件属于高敏感凭证，不得放入普通数据归档。

### FR-19 特殊频道店铺 URL 采集

系统应支持通过独立的 `telegram.shop_url_channels` 配置指定特殊频道。该配置中的每个来源必须同时存在于人工 `allowlist` 中，不能借此扩大采集范围。

对特殊频道的消息：

- 提取消息正文中带 `http://` 或 `https://` 的 URL；
- 提取消息正文中不带协议、但具有域名结构的店铺 URL；
- 带协议 URL 保留其协议；无协议域名规范化为可直接访问的 `https://` URL，并保存所属 `chat_id`、`message_id` 和采集时间；
- 同一消息中的重复 URL 不重复保存；
- 消息编辑后，以当前消息正文重新计算 URL 集合，删除已经不再存在的旧 URL；
- 首版只保存 URL，不抓取 URL 页面，不下载网页内容，不将 URL 页面内容发送给 AI。

### FR-20 消息链接和简介采集

系统应为普通采集来源的每条已保存消息保留消息链接 URL：

- 公开频道或群组优先使用 `https://t.me/<username>/<message_id>`；
- 无公开用户名但属于超级群组或频道时，使用 `https://t.me/c/<internal_id>/<message_id>`；
- 普通私有群组无法生成稳定链接时允许为空，不得伪造链接。

对 `telegram.shop_url_channels` 中的特殊来源不保存 Telegram 消息链接，只保存从正文提取的店铺 URL 和可取得的简介信息。

对特殊频道中可取得发送者公开资料的消息，只保存用户主页简介文本 `bio`：

- 简介直接附着在消息记录上；
- 不建立用户表；特殊频道消息落库时不保存发送者 ID、用户名、姓名、手机号、头像或其他身份资料；
- 不保留简介历史，只保留当前采集到的简介值；
- 无法读取简介时保存为空，不因简介读取失败阻塞消息采集；
- 简介仅作为文本资料保存，不用于区分或建立用户身份画像。

## 7. 非功能需求

### NFR-01 性能

在每天 1 万至 2 万条纯文本消息、清理前不超过约 26 万条活跃消息的条件下：

- 增量采集不得因 AI 总结而停止；
- 数据库写入应采用批量事务；
- 常用的按来源、时间范围查询应具有索引；
- 不允许逐条执行独立提交造成明显写入放大。

### NFR-02 可靠性

- 采集进程异常退出后应可重启恢复；
- 已提交消息不得重复；
- 未提交区间应通过补拉恢复；
- 同步游标必须晚于数据库提交更新；
- AI 总结和清理任务必须幂等。

### NFR-03 安全

- 所有敏感配置通过环境变量或受限配置文件提供；
- session 文件和环境文件仅允许运行账号读取；
- 不绕过 Telegram 权限；
- 不采集当前账号无权访问的内容；
- 不将 Telegram 数据用于模型训练或微调；
- 私密内容发送给第三方 AI 前，必须确认数据使用和隐私范围。

### NFR-04 可移植性

代码不得依赖 macOS 图形界面。

本机测试通过后，应能够在无图形界面的 Ubuntu 系统中通过：

- Python 虚拟环境；
- SSH 终端；
- `systemd` 服务；
- `systemd timer`；

完成运行和管理。

### NFR-05 可维护性

- 配置与代码分离；
- 采集、总结、清理职责分离；
- 错误信息应能定位到来源和任务；
- 数据库结构变更必须有迁移方式；
- 不在首版引入 Redis、Kafka、ClickHouse、Elasticsearch或向量数据库。

## 10. 本机验收标准

只有以下项目全部通过，才允许进入 Ubuntu 部署阶段。

### AC-01 登录

- 能在本机终端完成 Telegram 登录；
- 重启后可以复用 session；
- 日志不包含验证码或凭证。

### AC-02 来源识别

- 使用人工白名单中的真实频道完成测试；如白名单包含群组，则同时测试真实群组；
- 只采集白名单中明确启用的群组和频道；
- 能识别至少一个真实频道；
- 数据库使用稳定 `chat_id` 区分来源；
- 来源改名后不会产生新的重复来源。

### AC-03 首次同步

- 只拉取最近 6 个自然日；
- 消息按来源正确入库；
- 重复运行不产生重复消息；
- 中断后可以继续。

### AC-04 增量采集

- 新消息能够进入正确来源；
- 消息编辑能够更新原记录；
- 消息初始内容和每次不同的编辑内容均能在编辑历史中查询；
- 重复到达的相同编辑内容不会产生重复版本；
- 模拟断线后能够补拉缺失消息；
- AI 接口失败不影响继续采集。

### AC-05 AI 总结

- 能通过配置的 OpenAI 兼容 `base_url` 和模型调用总结接口；
- 至少为两个不同来源分别生成总结；
- 总结不会混合不同来源内容；
- 大批消息能够分块并合并；
- 每天能够在 `Asia/Shanghai` 的 08:00、12:00、22:00 创建总结任务；
- 三个窗口分别覆盖前一日 22:00 至当日 08:00、当日 08:00 至 12:00、当日 12:00 至 22:00；
- 调整三个执行时间后，窗口仍然连续且不重叠；
- 总结包含覆盖范围和代表性消息 ID；
- 总结使用“主题”“重要信息”“主要观点”“消息来源”中文固定栏目；
- 相同输入重复执行不会重复调用 AI。

### AC-06 清理

- 预览模式显示正确的时间范围和预计删除数量；
- 已总结成功和未总结成功的过期消息都会被强制删除；
- 过期原始消息对应的总结记录及 Markdown 文件同时删除；
- 来源、同步游标和清理记录不被删除；
- 总结失败不会延长原始消息保留时间；
- 重复执行清理不会报错或误删。

### AC-07 恢复

- 采集进程强制停止后可以恢复；
- SQLite 备份可以恢复并继续同步；
- 失败总结任务可以重试；
- 不因单个来源失败导致全部来源停止。

### AC-08 服务器兼容性检查

- 项目不依赖 GUI；
- 所有运行入口均可通过终端执行；
- 配置路径可以从本机切换到 Ubuntu；
- 已形成 Ubuntu 部署步骤草案；
- 未经用户明确批准，不执行服务器上传或部署。

### AC-09 特殊频道 URL 与简介

- `shop_url_channels` 中的来源必须已经存在于人工 `allowlist`；
- 特殊频道消息中带协议和不带协议的域名 URL 均能提取；
- 同一消息重复 URL 不产生重复记录；
- 消息编辑后 URL 集合与最新正文一致；
- 每条消息可查询其消息链接 URL；
- 特殊频道可读取的发送者简介能够保存到消息记录；
- 数据库中不存在用户主页表，特殊频道消息记录中的发送者身份字段为空；
- 简介读取失败不影响消息保存。

## 11. 当前非目标

当前版本不包含：

- 图片 OCR；
- 语音转写；
- 视频理解；
- 媒体文件下载；
- 多 Telegram 账号；
- 多用户权限系统；
- Web 管理后台；
- 跨服务器分布式采集；
- 消息全文搜索平台；
- 向量检索和知识问答；
- AI 模型训练或微调；
- 全部历史消息永久保存。

## 12. 已确认事项与剩余待确认事项

### 12.1 已确认事项

1. 目标来源采用人工白名单，不默认采集账号加入的全部群组和频道。
2. AI 使用 OpenAI 兼容接口，允许自定义 `base_url`、API 密钥和模型。
3. 默认每天在 `Asia/Shanghai` 的 08:00、12:00、22:00 执行总结，并允许修改执行时间。
4. 总结窗口以前一次计划执行时间为起点、本次计划执行时间为终点，连续且互不重叠。
5. 原始消息到期后强制删除，不因总结失败延长保留时间。
6. 总结记录和 Markdown 文件随对应原始消息到期删除，不长期保留。
7. 本机验收使用人工白名单中的真实频道；如白名单包含群组，则同时测试真实群组。测试保持只读采集，不向来源发送或修改消息。
8. 首个真实频道白名单为 `@hezu1`。
9. 总结使用中文固定结构，栏目为“主题”“重要信息”“主要观点”“消息来源”。
10. 消息保留初始版本和每次不同的编辑历史。
11. 清理任务默认在 `Asia/Shanghai` 每周日 03:00 执行。
12. 特殊频道使用独立 `shop_url_channels` 配置，提取带协议和不带协议的域名 URL。
13. 用户主页只保留简介文本，不区分用户身份，不保留用户资料历史。

### 12.2 剩余待确认事项

以下参数不阻止编码，但在真实 AI 联调前需要补充：

1. 实际使用的 OpenAI 兼容 `base_url`、模型名称及服务方数据隐私策略。
2. AI API 密钥仅在本机环境变量中配置，不写入本文档。

## 13. 需求变更规则

- 开始对应功能编码或本机联调前，应先确认第 12.2 节所需参数。
- 改变数据库结构、保留策略、消息范围或 AI 数据边界时，应同步更新本文档。
- 本机验收标准未全部通过前，不进入 Ubuntu 部署阶段。
- 任何服务器上传、部署、凭证迁移或长期服务创建，均需要用户再次明确授权。
